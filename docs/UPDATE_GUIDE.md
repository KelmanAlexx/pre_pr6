# Инструкция системного администратора по обновлению АРМ

**Документ:** UPDATE_GUIDE  
**Версия документа:** 1.0  
**Область применения:** клиентский модуль ИС «Умный кампус» на рабочих местах операторов.

## 1. Цель и общие правила

Инструкция описывает подготовку, проверку, установку и откат релиза клиентского ПО. Обновление выполняется централизованно, без участия оператора. Перед массовым развертыванием обязательно проверяется пилотная группа АРМ.

Центральный источник метаданных — `https://jsonplaceholder.typicode.com/posts/1`, а отправка метрик выполняется запросом POST на `https://jsonplaceholder.typicode.com/posts`.  ZIP-пакет в данной работе формируется локально из тестовых метаданных. Для эксплуатации требуется защищенное хранилище подписанных установочных пакетов.

## 2. Схема доставки и стратегия развертывания

Используется комбинация Canary Deployment и Blue-Green:

1. **Подготовка релиза.** Администратор публикует пакет, номер версии, контрольную сумму SHA-256 и описание изменений на центральном сервере.
2. **Canary — пилот.** Обновляется один тестовый АРМ или 1–5% рабочих мест. Проверяются запуск, вход, расписание, связь с сервером и сохранность данных.
3. **Первая волна.** При успешном пилоте обновляется небольшая группа (около 10%). В течение согласованного периода собираются журналы и метрики.
4. **Расширение.** При отсутствии критических ошибок обновляется следующая группа (например, 50%), затем остальные АРМ.
5. **Завершение.** Центральный сервер фиксирует версию каждого АРМ и результат установки.

На каждом отдельном АРМ применяется локальная схема Blue-Green: текущая версия хранится в каталоге `install/current`, новая распаковывается в `work/staging`. После проверки старая папка временно переименовывается в `rollback/previous`, а подготовленная версия становится активной. Если проверка не пройдена, выполняется обратное переключение.

## 3. Подготовка к обновлению

Перед запуском убедиться, что:

- релиз имеет согласованный номер и список изменений;
- контрольная сумма пакета получена по доверенному каналу;
- на АРМ достаточно свободного места для пакета и резервной копии;
- оператор завершил работу, клиент закрыт;
- нет активных операций записи в SQLite;
- известна предыдущая стабильная версия и доступна ее копия;
- определено окно обновления и ответственный администратор.

Параметры и пути в учебном проекте:

| Объект | Расположение внутри тестового каталога |
|---|---|
| Активный клиент | `install/current` |
| Подготовленная версия | `work/staging` |
| Предыдущая версия на время проверки | `rollback/previous` |
| Конфигурация | `data/appsettings.json` |
| Локальная БД | `data/campus.db` |
| Кэш | `data/cache/` |
| Резервные копии | `backups/<дата_время>/` |
| Журнал | `logs/upgrade.log` |
| Отчет проверки | `test-report.json` |

В сети доступ на запись должен иметь только служебный аккаунт обновления и администратор.

## 4. Резервное копирование

1. Отправить клиенту команду штатного завершения работы и дождаться освобождения файлов.
2. Убедиться, что процесс клиента завершен.
3. Скопировать `appsettings.json`, `campus.db` и весь каталог `cache` в новый каталог резервной копии с отметкой времени.
4. Рассчитать SHA-256 каждого файла и сохранить перечень в `backup-manifest.json`.
5. Повторно рассчитать SHA-256 уже скопированных файлов.
6. Сравнить контрольные суммы. При несовпадении обновление запрещено.

Для работы SQLite-файл копируется как обычный файл после остановки клиента. В промышленной системе при включенном WAL-режиме необходимо корректно завершить транзакции и выполнить контрольную точку либо использовать штатный механизм резервного копирования SQLite. Нельзя копировать только основной файл БД, если рядом остались незакрытые файлы `-wal` и `-shm`.

## 5. Установка обновления

1. Получить сведения о релизе и пакет по HTTPS.
2. Проверить HTTP-ответ и ограничение времени ожидания.
3. Проверить подпись пакета и SHA-256, полученную по доверенному каналу.
4. Распаковать пакет в отдельный временный каталог.
5. Проверить наличие обязательных файлов и совпадение версии в `version.txt`.
6. Создать и проверить резервную копию конфигурации, БД и кэша.
7. Переключить каталог `current` на подготовленный релиз.
8. Выполнить Sanity Test.
9. При успехе сохранить предыдущий релиз в архиве и зарегистрировать результат.
10. Отправить телеметрию. Ошибка телеметрии не должна отменять уже проверенное обновление.

## 6. Sanity Test и критерии приемки

| Проверка | Условие успешного результата |
|---|---|
| Версия | В `install/current/version.txt` указана целевая версия |
| Конфигурация | `appsettings.json` существует и разбирается как JSON-объект |
| SQLite | Файл существует, его SHA-256 совпадает с контрольной суммой резервной копии |
| Кэш | Каталог существует, пользовательские данные не потеряны |
| Файлы релиза | Присутствует `release-info.json` и основные файлы новой версии |
| Откат | При тестовом отказе восстановлена предыдущая версия и данные |
| Отчет | Создан `test-report.json`, ошибки и итоговый статус зафиксированы |

Дополнительно проверяются запуск интерфейса, авторизация тестового пользователя, чтение расписания, доступ к центральному серверу, права доступа и совместимость схемы БД.

## 7. План отката (Rollback Plan)

Откат выполняется при ошибке запуска, неуспешном Sanity Test, повреждении конфигурации, нарушении целостности данных или резком росте ошибок после релиза.

1. Остановить клиент и запретить дальнейшее обновление данного АРМ.
2. Зафиксировать ошибку и сохранить журнал текущего обновления.
3. Удалить неработающий каталог `install/current`.
4. Переместить `rollback/previous` обратно в `install/current`.
5. Восстановить `appsettings.json`, `campus.db` и `cache` из проверенной резервной копии, если данные могли измениться.
6. Проверить номер восстановленной версии и контрольные суммы.
7. Запустить клиент и выполнить короткую проверку входа и чтения расписания.
8. Отправить администратору отчет о неудачном релизе.
9. Приостановить распространение этой версии на остальные АРМ.

Если резервная копия повреждена или предыдущая версия не запускается, АРМ не возвращается в эксплуатацию до ручного восстановления администратором.

## 8. Запуск

Требуется .NET 8 SDK. Открыть `SmartCampusSilentUpgrade.sln` в Visual Studio 2022 и выше или выполнить команды из каталога проекта:

```powershell
# Штатное обновление с обращением к JSONPlaceholder
 dotnet run -- --scenario success --reset

# Имитация ошибки Sanity Test и автоматического отката
 dotnet run -- --scenario rollback --reset

# Те же сценарии без сети (для демонстрации в аудитории)
 dotnet run -- --scenario success --reset --offline
 dotnet run -- --scenario rollback --reset --offline
```

`--reset` пересоздает демонстрационное окружение с исходной версией 1.0.0. Не применять этот параметр к реальной рабочей установке. `--offline` отключает обращения к тестовому API и использует встроенные тестовые метаданные.

Коды завершения: `0` — обновление прошло успешно; `2` — установка завершилась ошибкой без подтвержденного отката; `3` — ошибка обновления обработана, предыдущая версия восстановлена.

## 9. Ограничения реализации и меры для промышленной эксплуатации

- Перед распаковкой внешних архивов в производстве нужно проверять подпись, размеры, количество файлов и запрещать выход путей за каталог распаковки.
- Для SQLite в производстве требуется согласованный механизм резервного копирования и миграций схемы. Изменения БД следует проектировать по принципу expand-contract, чтобы старая версия не теряла совместимость во время Canary.
- Журналы не должны содержать пароли, токены и персональные данные.
